### Q4. `num_output_placeholders` 那段 if 是什么意思？

**场景：** 异步调度 + 投机解码

**结论：**
- `num_output_placeholders`：已调度、输出尚未确认的在途 token 数（真实采样 + draft）
- `num_computed_tokens`：乐观提前增加的已调度位置
- 条件含义：若 **draft 全被拒、只接受 1 个真实 token 后也已到 max_tokens**，则本步 **不再调度**，避免多跑一步
- 公式：`num_computed_tokens + 2 - num_output_placeholders >= num_prompt_tokens + max_tokens`

---

### Q5. `next_decode_eligible_step` / `defer_prefills` / `num_new_tokens` 是什么？

**① PP + 异步 decode 节拍**
```python
if self.current_step < request.next_decode_eligible_step: continue
```
- V2 Model Runner + Pipeline Parallel：采样结果经 slot ring 在 **pp_size 步** 后才消费
- 调度侧设置 `next_decode_eligible_step = current_step + pp_size`，保证与 worker 对齐

**② DP prefill 平衡**
```python
if defer_prefills and request.is_prefill_chunk: continue
```
- 非 cadence 对齐步：有 decode 在跑时，**延后** 仍在 prefill 的请求
- decode 照常，避免 prefill 挤占算力、平衡多 DP rank 负载

**③ 本步算多少 token**
```python
num_new_tokens = (
    request.num_tokens_with_spec
    + request.num_output_placeholders
    - request.num_computed_tokens
)
```
- 统一公式：让 `num_computed_tokens` 追上「需要算到的总长度」
- 不硬分 prefill/decode 阶段；后面还会被 `token_budget`、`long_prefill_token_threshold` 截断

### Q6. Chunked prefill 是 PagedAttention 里的吗？PagedAttention 原理？

**结论：不是同一层概念**

| 概念 | 层级 | 解决什么 |
|------|------|----------|
| **PagedAttention** | 内存管理 | KV 按 block 分页存，block table 映射 |
| **Chunked prefill** | 调度策略 | 长 prompt 分多步算，不堵住 decode |

**PagedAttention 三要素：** Block Pool → Block Allocator → Block Table  
**互补关系：** chunked prefill 决定「这一步算哪段」；PagedAttention 决定「算了的 KV 占哪些 block」

---

### Q7. CXL 和 UB（灵衢）有什么区别？

| | CXL | UB |
|---|-----|-----|
| 定位 | PCIe 上开放标准，CPU 侧内存扩展 | 超节点统一互联协议 |
| 范围 | 机架内为主 | 机内 + 机间 |
| 中心 | CPU Host | CPU/NPU 对等 |
| AI 集群 | 补内存；机间仍靠 IB/RoCE | 内存 + 互联 + 通信一体化 |

---

### Q8. Harness 是什么？

**Harness = 把被测/被跑对象包起来的运行壳**（环境 + 输入 + 执行 + 度量）

常见类型：test harness、benchmark harness、eval harness（如 lm-eval-harness）、agent harness

vLLM 的 `benchmarks/` 是 benchmark harness，不是 PagedAttention 本身。

---

### Q9. CXL vs UB 内存池化方案对比

**已整理成文档（23 页 PPT + Markdown），核心结论：**
- **CXL-Pool**：x86/GPU 集群渐进扩 KV，Fabric Manager + CXL Switch + Type-3 DIMM
- **UB-Pool**：昇腾超节点，UBS Engine 内存借用/共享，NPU 直访池化 DDR
- 选型：已有 NVIDIA → CXL；已立项 Atlas 超节点 → UB

**文档位置（GitHub）：**
- Markdown：https://github.com/ghsshou/ai_work/blob/main/CXL_UB_内存池化与_UB_数据路径对比.md
- PPT：https://github.com/ghsshou/ai_work/blob/main/CXL_UB_内存池化与数据路径对比.pptx

### Q10. 「小包 LD/ST 效率高，大包 URMA 效率高」对吗？

**基本正确，需收窄表述：**

| 路径 | 适用 |
|------|------|
| **Load/Store（TP Bypass）** | 小 payload、低延迟、同步 CPU 访问 |
| **URMA Read/Write（Work-Queue）** | 大 payload、高吞吐、异步 DMA |

- LD/ST 不是与 URMA 对立，而是 URMA 内部的 fast path
- 64B 远端读：UB LD/ST ~500ns vs RoCE ~2200ns（OpenURMA）
- 经验 crossover：几 KB 以下偏 LD/ST，更大偏 Work-Queue（需实测）

## 四、已建立的核心直觉（应能复述）

1. **推理 ≠ 训练**：迭代式 `step()` 循环，每步可能只算 1 个 token（decode）或一段 prompt（prefill）
2. **vLLM 调度器不硬分阶段**：靠 `num_computed_tokens` 追上 `num_tokens_with_spec`
3. **PagedAttention 管内存，Chunked prefill 管时间片**
4. **昇腾差异在 `vllm_ascend/`**：调度逻辑与 GPU  largely 共用
5. **CXL/UB 是更底层互联**：影响 KV 能不能池化、跨节点怎么搬，不改变 PagedAttention 算法本身
