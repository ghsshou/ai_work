# 大模型负载驱动的昇腾超节点规模需求分析

> **用途：** 昇腾超节点产品规格定义与客户训练/推理负载选型  
> **版本：** v0.1  
> **日期：** 2026-08-11  
> **范围：** 技术最优规模；不讨论成本、功耗、散热和机柜约束  

---

## 摘要

超节点规模不是“卡越多越好”，也不能只用“模型能不能装下”判断。真正决定规模的是三件事：

1. **容量下界**：权重、训练状态、Activation 或 KV Cache 至少需要多少 HBM；
2. **性能下界**：目标训练速度、推理吞吐或时延至少需要多少算力与带宽；
3. **通信边界**：张量并行、专家并行和上下文并行产生的高频通信，是否应限制在同一个高速互联域内。

本文采用“双层推导法”。第一层从模型和负载计算容量、算力下界；第二层把负载映射到张量并行（TP）、专家并行（EP）、上下文并行（CP）、流水线并行（PP）和数据并行（DP），再通过通信时间和扩展效率确定合理的超节点边界。

对每类负载，本文不只给出一个卡数，而是区分：

- **最小可运行规模**：容量和基础算力能够满足要求；
- **性能推荐规模**：高频通信仍能获得高速互联收益；
- **扩展拐点**：继续扩大并行组后，通信、气泡或负载不均开始吞噬大部分收益；
- **集群总规模**：通过数据并行、流水线并行或多副本扩展，可能远大于单个超节点。

### 一页结论

| 负载 | 容量第一驱动因素 | 性能第一驱动因素 | 优先留在超节点内的并行域 |
|---|---|---|---|
| Dense 训练 | 参数、梯度、优化器状态 | TP 集合通信、PP 气泡 | TP，长序列时再加 CP |
| MoE 训练 | 全部专家权重与训练状态 | EP All-to-All、专家负载不均 | TP × EP，必要时再乘 CP |
| 长序列训练 | Activation | Attention 计算与 KV 交换 | TP × CP |
| Dense 在线推理 | 权重与 KV Cache | Decode HBM 带宽、TPOT | 满足单副本容量的最小有效 TP |
| 长上下文推理 | KV Cache | KV 读取、TTFT、调度 | TP，必要时加入 CP 或 KV 分层 |
| MoE 推理 | 全部驻留专家权重 | 被访问专家集合与 EP 通信 | TP × EP |
| 离线推理 | 权重副本 | 大 Batch 吞吐 | 优先多副本，避免无收益地增大 TP |
| PD 分离推理 | Decode 侧 KV 容量 | Prefill 算力、Decode 带宽、KV 传输 | P、D 可独立成组，互联需承载 KV |

**产品定义侧的核心判断：** 超节点至少应完整容纳主流负载的高频模型并行组，而不必把所有数据并行副本都放进同一个 Scale-up 域。

**客户选型侧的核心判断：** 先找出模型可运行的最小并行度，再判断扩大并行组是在降低时延，还是只在增加通信。推理尤其不能把“更多 TP”简单等同于“更高吞吐”。

## 1. 超节点规模问题是什么

### 1.1 本文中的“超节点”

本文把超节点定义为：

> 由低时延、高带宽 Scale-up 互联连接的一组 NPU，组内能够高效执行频繁的集合通信、All-to-All 或远程内存访问，并作为一个主要模型并行域进行调度。

这个定义关注的是**计算和通信边界**，不是机柜外形。它也不等同于整个训练集群或推理集群。

可以把大模型集群想成三层：

```text
单个 NPU
   ↓ 高速 Scale-up
超节点：承载高频模型并行
   ↓ Scale-out 网络
多超节点集群：承载 DP、PP、多副本和全局调度
```

### 1.2 三种容易混淆的规模

| 概念 | 回答的问题 |
|---|---|
| 模型并行组规模 | 一个模型副本需要多少 NPU 协同计算 |
| 单超节点规模 | 多少高频通信 rank 应位于同一个高速互联域 |
| 集群总规模 | 为达到总训练速度或总服务吞吐，需要多少 NPU |

例如，一个训练任务可能使用 1024 张 NPU，但其高频 TP×CP 组只有 16 张。此时“集群需要 1024 卡”并不意味着“单个超节点必须有 1024 卡”。其余规模可能来自 DP 副本或 PP stage。

### 1.3 为什么不是越大越好

扩大超节点有三个潜在收益：

- 能在一个高速域内容纳更大的模型并行组；
- 能把更多专家或更长序列的通信留在 Scale-up 网络；
- 能通过统一内存编址、KV共享或资源池化提升灵活性。

但单任务并行规模扩大后，也会出现：

- 每张 NPU 分到的计算变少，通信启动时延占比提高；
- All-to-All 的 peer 数和拥塞风险增加；
- Pipeline stage 或专家负载不均造成“快卡等慢卡”；
- 推理 TP 过大后，权重虽然切得更细，但每 Token 的集合通信更多；
- 单个小任务无法有效占满整个超节点。

因此，技术最优规模通常位于一条“容量足够、通信可控、计算仍饱满”的交叉线上。

## 2. 只保留影响规模的模型与负载参数

本文不展开 Transformer 工作原理，只保留会改变容量、计算或通信的变量。

### 2.1 符号

| 符号 | 含义 |
|---|---|
| \(P_{\text{total}}\) | 模型总参数量 |
| \(P_{\text{active}}\) | 每个 Token 实际激活的参数量 |
| \(L\) | Transformer 层数 |
| \(H\) | 隐藏维度 |
| \(F\) | FFN/专家中间维度 |
| \(E\) | Routed Expert 总数 |
| \(K\) | 每个 Token 选择的 Routed Expert 数 |
| \(N_{\text{KV}}\) | KV Head 数 |
| \(D_{\text{head}}\) | 单个 Head 维度 |
| \(S\) | 序列长度 |
| \(B\) | Micro Batch 或一次执行中的序列数，按上下文注明 |
| \(C\) | 系统中驻留的并发请求数 |
| \(b_w,b_a,b_{kv}\) | 权重、Activation、KV 每元素字节数 |
| \(G\) | 单个超节点的 NPU 数 |

### 2.2 Dense 与 MoE 只需要抓住两个参数

Dense 模型中：

\[
P_{\text{active}}\approx P_{\text{total}}
\tag{1}
\]

MoE 模型中：

\[
P_{\text{active}}\ll P_{\text{total}}
\]

这带来一个关键差异：

- **总参数量**决定模型和训练状态能否装入；
- **激活参数量**更接近每个 Token 的实际计算量。

因此，一个总参数量很大的 MoE 模型，单 Token FLOPs 可能只相当于较小的 Dense 模型，但它仍需要为未被当前 Token 选中的专家保留权重。

### 2.3 MoE 参数量

设每个专家参数量为 \(P_x\)，MoE 层数为 \(L_{\text{MoE}}\)，每层有 \(E\) 个 Routed Experts，每个 Token 激活 \(K\) 个专家。忽略较小的 Router 参数：

\[
P_{\text{MoE,total}}
\approx
P_{\text{nonexpert}}
+L_{\text{MoE}}E P_x
\tag{2}
\]

\[
P_{\text{MoE,active}}
\approx
P_{\text{nonexpert}}
+L_{\text{MoE}}K P_x
\tag{3}
\]

如果有 \(J\) 个每个 Token 都会经过的 Shared Experts，还应在式（2）、式（3）中加入对应参数。

对常见 SwiGLU 专家，若输入隐藏维度为 \(H\)，专家中间维度为 \(F\)：

\[
P_x\approx3HF
\tag{4}
\]

三个矩阵分别对应 gate、up 和 down 投影。实际模型可能使用不同中间维度或参数共享，因此式（4）用于量级估算。

### 2.4 序列长度为什么关键

序列长度 \(S\) 同时影响三类资源：

- 训练 Activation 通常近似随 \(S\) 线性增长；
- 稠密 Attention 的数学计算量包含 \(S^2\) 项；
- 推理 KV Cache 随驻留 Token 数线性增长。

FlashAttention 可以避免在 HBM 中保存完整的 \(S^2\) Attention 矩阵，但不会把精确稠密 Attention 的数学计算量自动降为线性。

### 2.5 推理中 Batch 与并发不是一回事

- \(C\)：已经占用 KV Cache、正在排队或运行的驻留请求；
- \(B\)：某一轮真正获得 Decode Token 的请求数。

Continuous Batching 下通常有：

\[
B\le C
\]

容量规划主要看 \(C\) 和驻留长度；每步计算与带宽摊销主要看 \(B\)。把两者混用，往往会高估吞吐或低估 KV 容量。

## 3. 不绑定型号的昇腾硬件抽象

为了让结论能跨代际复用，本文用以下参数描述一个 NPU 和一个超节点。

### 3.1 单 NPU 参数

| 参数 | 含义 |
|---|---|
| \(M_{\text{HBM}}\) | 单 NPU HBM 容量 |
| \(BW_{\text{HBM}}\) | HBM 峰值带宽 |
| \(F_{\text{peak}}(q)\) | 精度 \(q\) 下峰值算力 |
| \(\eta_F\) | 目标模型/算子上的可持续算力效率 |
| \(\eta_B\) | 目标访问模式上的可持续 HBM 带宽效率 |

有效算力和有效带宽写为：

\[
F_{\text{eff}}=\eta_FF_{\text{peak}}
\]

\[
BW_{\text{HBM,eff}}=\eta_BBW_{\text{HBM}}
\]

\(\eta_F,\eta_B\) 不能由产品峰值表直接推出，应通过目标模型、精度、Batch和算子实测。

### 3.2 超节点互联参数

| 参数 | 含义 |
|---|---|
| \(G\) | 超节点 NPU 数 |
| \(BW_{\text{link}}\) | 单 NPU 或单端点物理互联带宽 |
| \(BW_{\text{coll}}\) | 指定消息大小和 rank 数下的集合通信有效带宽 |
| \(\alpha\) | 一次通信的固定启动时延 |
| \(O\) | 拓扑超额订阅比 |
| \(D\) | 通信路径跳数或等效距离 |

物理端口带宽、总交换带宽和应用可获得的集合通信带宽是三个不同指标。超节点规模推导应优先使用 HCCL 在目标消息大小和拓扑下测得的 \(BW_{\text{coll}}\)。

### 3.3 内存不是只有 HBM

昇腾超节点可能还包含：

- 本地 CPU DDR；
- 统一编址或池化内存；
- 经 UB 访问的远端内存；
- 外部存储或 KV Cache 分层。

这些层级可以扩大可服务容量，但不能无条件替代 HBM。是否适合放置 KV、Activation 或权重，取决于访问频率、带宽、时延和是否可与计算重叠。

报告中应分别写：

```text
容量够不够？
带宽够不够？
时延是否进入关键路径？
```

只回答第一问，不能证明某种内存层级可以支撑目标性能。

## 4. 双层规模推导法

### 4.1 第一层：容量和算力下界

设所有需要驻留的内存为 \(M_{\text{total}}\)，每张 NPU 只计划使用 \(\eta_M\) 比例的 HBM：

\[
N_{\text{memory}}
=
\left\lceil
\frac{M_{\text{total}}}
{M_{\text{HBM}}\eta_M}
\right\rceil
\tag{5}
\]

\(\eta_M\) 用于预留 Runtime Workspace、通信 Buffer、分页碎片及短时峰值。它应由软件栈实测确定，而不是固定常数。

设一个目标时间窗口内需要完成的有效计算量为 \(F_{\text{required}}\)，目标完成时间为 \(T_{\text{target}}\)：

\[
N_{\text{compute}}
=
\left\lceil
\frac{F_{\text{required}}}
{F_{\text{peak}}\eta_FT_{\text{target}}}
\right\rceil
\tag{6}
\]

一级下界为：

\[
N_{\min}
=
\max(N_{\text{memory}},N_{\text{compute}})
\tag{7}
\]

这只是“能装下、理论上能按时算完”，尚未考虑并行切分是否可行以及通信是否过重。

### 4.2 第二层：把并行维度映射到拓扑

常用并行维度包括：

- **TP，张量并行**：一层矩阵由多张 NPU 协同完成，几乎每层都通信；
- **EP，专家并行**：不同专家放在不同 NPU，Token 每个 MoE 层都要重新分发；
- **CP，上下文并行**：序列切到不同 NPU，Attention 期间交换 KV；
- **PP，流水线并行**：不同层放在不同 Stage，边界传 Activation；
- **DP，数据并行**：复制模型、处理不同数据，优化步骤同步梯度；
- **Replica，推理副本**：多个独立模型实例服务不同请求。

在标准正交并行布局下，一个模型并行组规模为：

\[
N_{\text{MP}}
=TP\times EP\times CP\times PP
\tag{8}
\]

但并非所有维度都必须位于同一个超节点。通常应优先把通信频率最高、最难隐藏的部分留在 Scale-up 域：

\[
N_{\text{high-freq}}
\approx TP\times EP\times CP
\tag{9}
\]

式（9）是**候选边界**，不是绝对产品卡数。实际实现可能复用 rank、采用层次化 EP、跨节点 CP，或让 PP stage 跨越超节点。

### 4.3 通信时间

对大小为 \(V\) 的消息，最基础的 \(\alpha-\beta\) 模型为：

\[
T_{\text{comm}}
\approx n_\alpha\alpha+\frac{V}{BW_{\text{effective}}}
\tag{10}
\]

- 小消息或大量同步点主要受 \(\alpha\) 影响；
- 大消息主要受有效带宽影响；
- 拥塞、跳数、协议和超额订阅会降低 \(BW_{\text{effective}}\)。

如果通信与计算能够重叠，Step 时间不应简单相加：

\[
T_{\text{step}}
\approx
T_{\text{nonoverlap}}
+
\max(T_{\text{compute}},T_{\text{overlapped comm}})
+
T_{\text{bubble}}
+
T_{\text{imbalance}}
\tag{11}
\]

### 4.4 扩展效率与拐点

模型无法在单卡运行时，可选一个基准规模 \(N_0\)：

\[
E(N;N_0)
=
\frac{\text{Throughput}(N)}
{(N/N_0)\text{Throughput}(N_0)}
\tag{12}
\]

当规模增加而 \(E(N;N_0)\) 持续下降，说明额外 NPU 更多地用于等待通信，而不是增加有效计算。

本文把“扩展拐点”定义为业务和产品共同设定的阈值，例如：

- 扩展效率低于目标值；
- 通信暴露时间超过 Step 时间的一定比例；
- 推理 TPOT 不再改善；
- 单专家 Token 数低于高效 GEMM 所需批量；
- PP 气泡或专家负载不均成为首要瓶颈。

阈值必须由产品目标指定。没有吞吐、时延或效率目标，就只能得到容量下界，不能得到唯一的技术最优卡数。

## 5. 从公式到产品和客户决策

### 5.1 产品定义流程

```text
建立目标模型/负载集合
        ↓
为每个负载求最小容量与算力
        ↓
枚举 TP/EP/CP/PP 候选组合
        ↓
计算高频通信组和通信暴露时间
        ↓
找出各负载扩展拐点
        ↓
统计不同超节点规模对目标负载的覆盖率
```

产品规模不应由单个最大模型决定，而应由目标负载集合中“高频并行组”的分布决定。最大模型可以通过 PP 或多超节点扩展；如果为了极少数负载把全部集群都放入一个 Scale-up 域，可能导致大量常见任务无法有效利用。

### 5.2 客户选型流程

```text
模型结构与精度
 → 单副本容量
 → 训练状态/Activation 或 KV
 → 最小模型并行度
 → 目标吞吐/时延
 → 并行策略
 → 是否跨超节点
 → Benchmark 校准
```

客户最终得到的不是一个孤立卡数，而是一组配置：

```text
单模型并行组大小
× 模型副本或 DP 数
× PP stage 数
= 集群总卡数
```

### 5.3 解析模型的角色

解析公式适合：

- 排除明显不可行的方案；
- 解释参数变化的方向和量级；
- 缩小需要 Benchmark 的配置空间；
- 找出对结果最敏感的变量。

解析公式不能替代：

- HCCL 在目标拓扑上的实测；
- 目标模型的 Kernel 效率；
- 路由倾斜和真实请求长度分布；
- 调度、内存碎片、容错和系统软件开销。

## 6. Dense 模型训练需要多大超节点

Dense 训练的规模推导可以分为四步：

```text
训练状态能否装下
 → Activation 能否装下
 → TP/PP 如何切分
 → TP 高频通信是否适合当前超节点
```

### 6.1 训练状态内存

经典 BF16/FP16 混合精度 Adam 训练常采用以下一级估算：

| 状态 | 每参数字节数 |
|---|---:|
| BF16/FP16 计算权重 | 2 |
| BF16/FP16 梯度 | 2 |
| FP32 Master Weight | 4 |
| Adam 一阶矩 | 4 |
| Adam 二阶矩 | 4 |
| 合计 | 16 |

因此：

\[
M_{\text{state}}\approx16P_{\text{total}}
\tag{13}
\]

这条公式的价值是快速判断量级。例如，1000 亿参数模型仅训练状态就约为 1.6 TB。

它不是所有训练栈的固定常数：

- 部分 BF16 Optimizer 不保留 FP32 Master Weight，可能接近 12 Bytes/Parameter；
- 梯度格式、量化优化器和临时 Buffer 会改变峰值；
- 式（13）不含 Activation、通信桶和算子 Workspace。

### 6.2 ZeRO 如何改变单卡内存

设 TP×PP 已把每个模型副本的参数切为：

\[
P_{\text{local}}
\approx\frac{P_{\text{total}}}{TP\times PP}
\]

DP 度为 \(D\)。在上述 16 Bytes/Parameter 口径下：

\[
M_{\text{ZeRO-1}}
\approx
\left(4+\frac{12}{D}\right)P_{\text{local}}
\]

\[
M_{\text{ZeRO-2}}
\approx
\left(2+\frac{14}{D}\right)P_{\text{local}}
\]

\[
M_{\text{ZeRO-3}}
\approx
\frac{16P_{\text{local}}}{D}
\tag{14}
\]

直觉上，ZeRO-1 分片 Optimizer State，ZeRO-2 再分片 Gradient，ZeRO-3 再分片 Parameter。

但 ZeRO-3 会引入参数 All-Gather 和 Reduce-Scatter。它可以降低容量下界，却不代表通信代价为零。产品规格分析应同时比较：

```text
增加 TP/PP 以切模型
vs.
增加 DP/ZeRO 以切状态
```

两者可能得到相同的单卡内存，却具有完全不同的通信模式。

### 6.3 Activation 内存

用于大众理解的一级公式是：

\[
M_{\text{activation}}
\approx
c_{\text{act}}
\frac{B_{\mu}SL_{\text{stage}}H b_a}{TP}
\times N_{\text{inflight}}
\tag{15}
\]

- \(B_{\mu}\)：Micro Batch；
- \(L_{\text{stage}}\)：当前 PP Stage 持有的层数；
- \(N_{\text{inflight}}\)：流水线上同时驻留的 Micro Batch；
- \(c_{\text{act}}\)：由算子、重计算和保存策略决定的系数。

式（15）强调趋势：Activation 随 Micro Batch、序列长度、层数和隐藏维度增加。

更精细的 Megatron 工程模型包含线性项和普通 Attention 的平方项：

\[
M_{\text{act,layer}}
\approx
34SB_{\mu}H
+5N_{\text{head}}B_{\mu}S^2
\]

系数 34 和 5 来自特定 GPT 实现，只适合容量估算。采用 FlashAttention 或选择性重计算后，通常不再需要长期保存完整的 \(S^2\) Attention 中间量，式（15）的线性表达更接近主项。

### 6.4 训练计算量

Dense Transformer 训练最常用的主项近似为：

\[
F_{\text{train}}
\approx6P_{\text{total}}T
\tag{16}
\]

\(T\) 为训练 Token 数。直觉是：

- 前向：约 2 FLOPs/Parameter/Token；
- 反向输入梯度与权重梯度：合计约 4 FLOPs/Parameter/Token。

长序列时还要显式加入 Attention：

\[
F_{\text{attn,train}}
\approx12LB_{\mu}S^2H
\tag{17}
\]

式（16）适合估算模型矩阵乘主项，式（17）解释为什么序列很长时，单纯使用 \(6PT\) 会低估计算。

### 6.5 TP 为什么优先留在超节点内

定义一个 Micro Batch 的主要 Activation Tensor：

\[
A=b_aB_{\mu}SH
\]

标准 Megatron 式 TP 在每层会执行多次 All-Reduce 或等价的 All-Gather/Reduce-Scatter。采用 Ring All-Reduce，\(r=TP\)：

\[
T_{\text{AR}}
\approx
2(r-1)\alpha+
2\frac{r-1}{r}\frac{A}{BW_{\text{coll}}}
\tag{18}
\]

关键不只是总字节量，而是 TP 通信**每层、每个 Micro Batch 都发生**。因此：

- TP 对低时延敏感；
- TP 对集合通信有效带宽敏感；
- TP 跨越 Scale-out 网络通常比 PP 或 DP 更容易暴露在关键路径。

### 6.6 PP 与 DP 为什么更容易跨超节点

PP 每个 Stage 边界主要发送 Activation 和反向梯度，频率低于逐层 TP，但会产生流水线气泡。若有 \(p\) 个 Stage、\(m\) 个 Micro Batch，基础流水线利用率近似：

\[
U_{\text{pipeline}}
\approx
\frac{m}{m+p-1}
\tag{19}
\]

增加 PP 可以降低每个 Stage 的参数和 Activation，但如果 Micro Batch 数不足，更多设备会耗在流水线填充与排空上。

DP 通常每个 Optimizer Step 同步梯度，而不是每层同步。梯度累积还能摊薄同步频率。因此在拓扑映射上常采用：

```text
超节点内：TP，必要时 CP
超节点间：PP、DP
```

这是一条优先级原则，不是固定规则。大梯度同步仍可能需要高带宽 Scale-out 网络，PP Stage 边界也需检查实际 Activation 大小。

### 6.7 Dense 训练的规模结论

对一个给定模型，建议按以下顺序选择：

1. 计算普通训练、ZeRO或FSDP下的单卡状态内存；
2. 加入 Activation、Workspace和预留；
3. 找到最小可行 TP×PP；
4. 优先增加 PP 解决“层数可切分”的容量问题；
5. 仅在单层矩阵或目标性能需要时扩大 TP；
6. 用 HCCL 实测检查 TP 扩展效率；
7. 将 DP 作为总训练吞吐的主要扩展维度。

因此，Dense 训练对单超节点规模的主要要求通常不是整个集群卡数，而是：

\[
G_{\text{Dense}}
\gtrsim TP\times CP
\]

PP 是否完整位于超节点内，应由 Stage 通信、故障域和调度方式决定。

## 7. MoE 训练：专家数为什么会改变超节点规模

MoE 的难点在于“容量、计算和通信由不同参数决定”。

### 7.1 三条必须分开的链路

```text
E（专家总数）
 → 总参数与权重容量

K（每 Token 激活专家数）
 → 单 Token 专家计算与基本通信 payload

EP（专家并行度）
 → 每卡专家数、通信 peer 数和通信边界
```

增加 \(E\) 而保持 \(K\) 不变，单 Token 的理论专家计算不会同比增加，但会出现：

- 更多专家权重需要驻留；
- 为维持每卡专家数，EP 可能增大；
- 单专家收到的 Token 变少，小 GEMM 效率下降；
- 路由方差和最慢 Rank 尾部延迟更明显。

### 7.2 专家容量

设一个 EP 通信组本层处理 \(N=BS\) 个 Token，每个 Token 选择 \(K\) 个专家，则 Token-Expert Assignment 总数为：

\[
N_{\text{assign}}=BSK
\]

若 Capacity Factor 为 \(c\)，且按 Assignment 平均数定义，则单专家容量：

\[
C_x
=
\left\lceil
c\frac{BSK}{E}
\right\rceil
\tag{20}
\]

这里必须说明 \(BS\) 是一个 EP 组的 Token 数。不同框架可能已经把 \(K\) 包含在“Token 数”定义中，不能只抄公式而不统一口径。

对固定容量 Padding 的实现，专家总计算槽位约为：

\[
EC_x\approx cBSK
\]

对 Dropless、动态 Packed 实现，Capacity Factor 不一定线性放大通信量；负载不均更多表现为动态 Buffer、稀疏计算和尾部延迟。

### 7.3 EP All-to-All 通信量

每个 Assignment 携带一个 \(H\) 维 Activation，每元素 \(b_a\) 字节。定义：

\[
X=BSKHb_a
\]

一次 Dispatch 或一次 Combine 的 EP 组级逻辑 Payload 约为 \(X\)。一次完整前向包含 Dispatch 和 Combine：

\[
V_{\text{EP,fwd}}^{\text{logical}}
\approx2BSKHb_a
\tag{21}
\]

若专家均匀放置，约 \(1/EP\) 的 Assignment 留在本 Rank，实际穿过互联的远端 Payload：

\[
V_{\text{EP,fwd}}^{\text{remote}}
\approx
2BSKHb_a
\left(1-\frac{1}{EP}\right)
\tag{22}
\]

训练前向加反向，在通信精度相同时近似再乘 2。

式（21）、式（22）最容易被误用。必须区分：

| 口径 | 含义 |
|---|---|
| 组级逻辑 Payload | 包含发往本 Rank 的数据 |
| 组级远端 Egress | 实际离开源 Rank 的总量 |
| 单 Rank 注入量 | 组级流量除以 EP 后的平均发送量 |
| Fabric Byte-hop | 流量再乘实际路由跳数 |
| Send+Receive 统计 | 可能把同一字节在两端统计两次 |

不能把这些口径都叫作“总网络流量”。

### 7.4 Expert 数不直接出现在基本 Payload 中

式（21）没有显式的 \(E\)，不代表专家数不影响通信性能。

随着 \(E\) 增加：

- 为保持每卡专家数，EP 通常增大；
- 远端概率趋近 1；
- All-to-All peer 数增加；
- 每个 peer 的消息变小，启动时延占比提高；
- 路由矩阵更稀疏、更不均匀；
- 单专家平均 Assignment：

\[
\bar n_x=\frac{BSK}{E}
\tag{23}
\]

不断下降。

因此，大专家数模型可能在“总字节量没有明显增加”的情况下，仍因小消息、负载不均和小 GEMM 而降低效率。

### 7.5 专家负载倾斜

设专家 \(e\) 收到 \(n_e\) 个 Assignment：

\[
\rho_{\text{expert}}
=
\frac{\max_e n_e}{BSK/E}
\tag{24}
\]

如果 Rank \(r\) 持有专家集合 \(\mathcal E_r\)，其总负载为：

\[
L_r=\sum_{e\in\mathcal E_r}n_e
\]

Rank 级倾斜：

\[
\rho_{\text{rank}}
=
\frac{\max_rL_r}{BSK/EP}
\tag{25}
\]

MoE Step 时间通常由最慢 Rank 决定。即使总 Assignment 数不变，热门专家也会让部分 Rank 同时面临更高接收带宽和更多专家计算。

Shared Experts 和冗余专家可以改善部分问题，但不是免费能力：

- Shared Experts 增加固定计算与权重占用；
- 冗余专家增加物理权重副本；
- 训练中的参数副本还需要同步；
- 专家复制可以降低热点和远端比例，但不会自动减少语义上的 Top-K。

### 7.6 TP×EP 联合通信域

专家权重理想单 Rank 占用：

\[
P_{\text{expert/rank}}
\approx
\frac{EP_{\text{count}}P_x}
{EP\times TP_x}
\tag{26}
\]

其中 \(TP_x\) 是专家内部的 TP 度。典型实现中，EP All-to-All 搬运完整 Hidden State，随后专家内部执行 TP 的 All-Gather/Reduce-Scatter。

因此，不能因为专家权重被 TP 切分，就直接把式（21）的 EP Payload 除以 TP。EP 和 TP 是两套不同通信。

若要求这两套高频通信都留在超节点内：

\[
G_{\text{MoE}}
\gtrsim TP\times EP
\tag{27}
\]

若再叠加长序列 CP：

\[
G_{\text{MoE,long}}
\gtrsim TP\times EP\times CP
\tag{28}
\]

### 7.7 MoE 的扩展拐点

MoE 推荐规模至少同时满足：

\[
\frac{EP_{\text{count}}P_x}
{EP\times TP_x}
\le M_{\text{expert budget/rank}}
\]

\[
\frac{BSK}{E}
\ge n_{\text{min,GEMM}}
\]

\[
T_{\text{A2A}}+T_{\text{TP,exposed}}
\lesssim T_{\text{expert compute}}
\]

其中 \(n_{\text{min,GEMM}}\) 由目标专家宽度和 NPU Kernel 实测确定。

MoE 超节点规模不应简单等于专家数。正确问题是：

> 为了让专家权重装下、单专家计算仍足够饱满、EP通信不跨越低速网络，至少需要多大的 TP×EP 高频域？

## 8. 长序列训练：容量问题会转化为通信问题

### 8.1 Attention 计算仍有平方项

标准精确 Attention：

\[
\operatorname{Attention}(Q,K,V)
=
\operatorname{softmax}
\left(\frac{QK^\top}{\sqrt{D_{\text{head}}}}\right)V
\]

完整 MHA 前向的 Attention 主项约为：

\[
F_{\text{attn,fwd}}
\approx4B_{\mu}S^2H
\tag{29}
\]

训练前向加反向约为式（17）的 \(12LB_{\mu}S^2H\)。

FlashAttention 通过分块减少 HBM 读写和中间存储，但仍计算精确 Attention：

\[
M_{\text{attention intermediate}}:O(S^2)\rightarrow O(S)
\]

\[
F_{\text{attention}}:O(S^2H)\quad\text{不变}
\]

### 8.2 CP 如何切长序列

CP 将序列切到 \(CP=c\) 个 Rank。每个 Rank 只保存约 \(S/c\) 个 Query，但 Attention 需要访问其他 Rank 的 KV。

设 BF16/BF16-like Activation 每元素 \(b_a\) 字节，标准 MHA 中一次 KV Ring All-Gather 的单 Rank 流量量级为：

\[
V_{\text{KV,AG/rank}}
\approx
2b_aB_{\mu}SH
\frac{c-1}{c}
\tag{30}
\]

系数 2 对应 K 和 V。GQA 时 KV 流量可按 KV Head 比例下降。

CP 带来的效果是：

- 单 Rank Activation 和 Attention 计算下降；
- 总 Attention 工作量不变；
- 每层增加 KV 交换；
- \(c\) 继续增大时，通信收益逐渐饱和。

### 8.3 长序列规模结论

长序列训练常见的合理映射为：

```text
超节点内：TP × CP
超节点间：PP × DP
```

但 CP 是否必须完全在超节点内，要比较：

\[
T_{\text{CP,exposed}}
\quad\text{与}\quad
T_{\text{attention/rank}}
\]

长序列使每 Rank Attention 计算也很大，因此部分通信可能被计算覆盖。真正的拐点需要按序列长度、GQA比例、CP算法和UB有效带宽实测。

### 8.4 三个常见误判

1. **只看 Activation 容量，不看 Attention FLOPs。**  
   FlashAttention 解决存储和 IO，不会消除所有 Token 两两交互。

2. **把 CP 扩展理解为 \(S^2/c^2\)。**  
   总工作量仍是 \(O(S^2H)\)，单 Rank通常约为 \(O(S^2H/c)\)。

3. **认为序列越长，超节点必须按同样比例扩大。**  
   重计算、FlashAttention、PP和Micro Batch调整也能降低单 Rank 容量；超节点规模最终由 TP×CP 的性能拐点决定。

## 9. 推理负载：同一个模型为什么会需要不同规模

推理不是缩小版训练。训练通常在较大矩阵上追求总吞吐；推理同时包含：

- **Prefill**：一次处理 Prompt 的多个 Token，计算密集；
- **Decode**：每轮通常为每个请求生成一个 Token，频繁读取权重和历史 KV；
- **调度与缓存**：请求不断加入、退出，Batch 和上下文长度动态变化。

因此，推理规模必须同时回答：

```text
模型和 KV 能不能装下？
Prefill 是否满足 TTFT？
Decode 是否满足 TPOT？
总副本数是否满足吞吐？
```

### 9.1 权重容量

未量化权重的一级公式：

\[
M_W\approx P_{\text{total}}b_w
\tag{31}
\]

TP 度为 \(p\) 时，更可靠的单 Rank 近似为：

\[
M_{W,r}
\approx
\frac{M_{W,\text{shard}}}{p}
+M_{W,\text{replicated}}
+M_{\text{quant metadata}}
+M_{\text{runtime}}
\tag{32}
\]

只有所有权重都能均匀切分且没有复制项时，才可简化为 \(M_W/p\)。

量化时还要计入：

- Group Scale；
- Zero Point；
- 对齐与 Padding；
- 反量化 Workspace；
- 部分未量化层。

所以“参数量×位宽”适合一级估算，不等于实际模型文件或 HBM 占用。

### 9.2 KV Cache

每个 Token 的逻辑 KV Cache：

\[
m_{\text{KV/token}}
=
2L N_{\text{KV}}D_{\text{head}}b_{kv}
\tag{33}
\]

系数 2 对应 Key 和 Value。并发请求 \(i\) 的驻留长度为 \(\ell_i\)：

\[
M_{\text{KV,total}}
=
m_{\text{KV/token}}
\sum_{i=1}^{C}\ell_i
\tag{34}
\]

在 MHA、GQA、MQA 中：

\[
N_{\text{KV}}
=
\begin{cases}
N_Q,&\text{MHA}\\
1<N_{\text{KV}}<N_Q,&\text{GQA}\\
1,&\text{MQA}
\end{cases}
\]

相对于 MHA，GQA 的逻辑 KV 容量约下降到 \(N_{\text{KV}}/N_Q\)。

### 9.3 TP 下 KV 不一定均匀除

若 KV Head 能按 TP 均匀切分：

\[
N_{\text{KV},r}=\frac{N_{\text{KV}}}{TP}
\]

但当 \(TP>N_{\text{KV}}\) 时，部分框架会复制 KV Head。此时应按单 Rank 实际 Head 数计算：

\[
m_{\text{KV/token},r}
=
2L N_{\text{KV},r}D_{\text{head}}b_{kv}
\tag{35}
\]

全 TP 组的物理 KV 放大率：

\[
\rho_{\text{KV}}
=
\frac{\sum_rN_{\text{KV},r}}{N_{\text{KV}}}
\tag{36}
\]

对于 MQA，如果每个 TP Rank 都复制唯一 KV Head，\(\rho_{\text{KV}}\) 可能等于 TP，而不是 1。

### 9.4 分页与容量高水位

设 KV Block 大小为 \(g\) Token，单 Rank HBM 约束：

\[
M_{\text{HBM},r}
\ge
M_{W,r}
+
m_{\text{KV/token},r}
\sum_{i=1}^{C}
g\left\lceil\frac{\ell_i}{g}\right\rceil
+
M_{\text{workspace}}
+
M_{\text{safety}}
\tag{37}
\]

分页减少外部碎片，但最后一个 Block 仍可能未填满。

容量规划不应只使用平均长度。长输出请求驻留更久，天然更容易出现在系统快照中。固定输入长度 \(S_{\text{in}}\)、输出长度 \(S_{\text{out}}\) 时，Decode Token 状态的平均上下文长度近似：

\[
\bar\ell
\approx
S_{\text{in}}+\frac{S_{\text{out}}-1}{2}
\tag{38}
\]

真实业务应采用 Token-time 加权分布和 P95/P99 高水位，而不是简单的平均输入加平均输出一半。

### 9.5 Prefill 计算

Prefill 的参数矩阵主项：

\[
F_{\text{prefill}}
\approx
2P_{\text{active}}S
+
c_{\text{attn}}LS^2H
\tag{39}
\]

- 第一项是权重矩阵作用于所有 Prompt Token；
- 第二项是 Attention；
- \(c_{\text{attn}}\) 取决于是否按因果三角区域执行以及 FLOPs 口径。

Prefill 通常具有较大的矩阵维度，较容易利用 NPU 计算单元。长 Prompt 时 \(S^2\) Attention 会进入 TTFT 关键路径。

Chunked Prefill 可以把长 Prompt 分段调度，避免单个请求长时间占满计算资源，但不会减少总模型计算量；它主要改变调度粒度和尾延迟。

### 9.6 Decode 计算

已有上下文长度为 \(\ell\)，生成一个 Token：

\[
F_{\text{decode/token}}
\approx
2P_{\text{active}}
+4LH\ell
\tag{40}
\]

第一项来自权重矩阵，第二项来自新 Query 与历史 KV 的 Attention。长上下文时，第二项和 KV 读取不能忽略。

MoE Decode 中，\(P_{\text{active}}\) 只适合计算 FLOPs；权重流量取决于本轮 Batch 中所有 Token 访问到的专家并集，而不是简单等于单 Token 激活参数。

### 9.7 Decode 的 Roofline 下界

单 Rank 一轮 Decode 的 HBM 流量可写为：

\[
Q_r
\approx
M_{W,r}^{\text{touched}}
+
m_{\text{KV},r}\sum_{i=1}^{B}\ell_i
+
B m_{\text{KV/token},r}
+
Q_{\text{activation}}
\tag{41}
\]

理想 Step 时间下界：

\[
t_{\text{step}}
\ge
\max
\left(
\frac{F_r}{\eta_FF_{\text{peak}}},
\frac{Q_r}{\eta_BBW_{\text{HBM}}}
\right)
+
t_{\text{comm,nonoverlap}}
\tag{42}
\]

算术强度：

\[
AI=\frac{F_r}{Q_r}
\tag{43}
\]

Dense Decode 在权重读取主导、Batch融合良好时：

\[
AI_{\text{weight}}
\approx
\frac{2B}{b_w}
\]

这解释了 Batch 的作用：同一轮读取的权重可以服务多个 Token，聚合吞吐随 \(B\) 提升。但单请求 TPOT 取决于整轮 Step 时间，不会除以 \(B\)。

### 9.8 在线与离线推理的规模选择

#### 在线低时延

优先目标：

- 满足 TTFT、TPOT的高分位；
- 控制排队；
- 保留足够 KV 容量；
- 避免为了切权重而使用过大的 TP。

推荐方法：

1. 选能容纳权重和目标 KV 高水位的最小 TP；
2. 检查该 TP 下的 Decode TPOT；
3. 若时延仍不满足，再增加 TP；
4. 总吞吐优先通过增加副本扩展。

#### 离线高吞吐

离线推理通常可以使用更大 Batch。若一个较小 TP 组已能放下模型，多副本经常比继续扩大 TP 更有效：

\[
N_{\text{total}}
=N_{\text{replica}}\times TP_{\text{per replica}}
\]

扩大 TP 会切分权重，但也增加逐层通信；多副本则让每个模型独立处理不同 Batch。

### 9.9 推理指标

首 Token 时延：

\[
TTFT
=t_{\text{queue}}+t_{\text{schedule}}
+t_{\text{prefill}}+t_{\text{first sample}}
\tag{44}
\]

每输出 Token 平均时间：

\[
TPOT_i
=
\frac{t_{i,\text{last}}-t_{i,\text{first}}}
{S_{\text{out},i}-1}
\tag{45}
\]

系统输出吞吐：

\[
TPS_{\text{out}}
=
\frac{\sum_iS_{\text{out},i}}
{T_{\text{benchmark}}}
\tag{46}
\]

必须同时说明：

- 开环到达率还是闭环固定并发；
- 平均值还是 P99；
- TPOT 还是所有 Token 的 ITL；
- 是否包含排队和网络；
- 输入/输出长度分布。

没有这些口径，“每秒多少 Token”无法用于超节点选型。

### 9.10 MoE 推理

MoE 推理需要同时考虑：

- 全部专家权重的 HBM 容量；
- 每 Token 的 Top-K 专家计算；
- Batch 内被访问专家的并集；
- EP All-to-All；
- 热门专家和专家复制；
- 单专家 Micro Batch 是否足够大。

小 Batch、低时延 Decode 下，专家数过多会让每个专家收到的 Token 很少。即使总 FLOPs 不高，也可能因大量小 GEMM 和 All-to-All 启动开销而低效。

因此 MoE 推理的推荐超节点规模不是简单追求最大 EP，而是寻找：

\[
\text{专家可驻留}
\quad\land\quad
\text{EP通信可控}
\quad\land\quad
\text{单专家Batch足够}
\]

### 9.11 Prefill/Decode 分离

PD 分离让 Prefill 和 Decode 独立扩容，但需要传输 Prompt KV。

单请求 Prompt KV 逻辑传输量：

\[
D_{\text{KV}}(S)
=
2LSN_{\text{KV}}D_{\text{head}}b_{kv}
\tag{47}
\]

若请求到达率为 \(\lambda\)：

\[
BW_{\text{PD,required}}
\ge
\frac{\lambda E[D_{\text{wire}}]}
{\eta_{\text{network}}}
\tag{48}
\]

\(D_{\text{wire}}\) 还需考虑：

- Prefill与Decode的TP布局重排；
- KV Head复制；
- 协议头、对齐和压缩；
- 是否逐层流水传输；
- P99 Prompt和突发到达；
- 多个 Prefill Rank 向同一 Decode Rank 的 Incast。

平均带宽满足式（48）不代表 P99 TTFT/TPOT 满足。PD 分离的价值是让计算型 Prefill 和带宽型 Decode 使用不同规模与调度策略，而不是消除通信。

## 10. 通信如何确定超节点边界

### 10.1 五类并行的通信特征

| 并行方式 | 主要通信 | 发生频率 | 对 Scale-up 的敏感度 |
|---|---|---:|---|
| TP | All-Reduce/All-Gather/Reduce-Scatter | 每层、每Micro Batch | 很高 |
| EP | All-to-All Dispatch/Combine | 每个 MoE 层 | 很高 |
| CP | KV Ring/All-Gather | 每个 Attention 层 | 高 |
| PP | Stage边界点对点 | 每个Micro Batch、每边界 | 中 |
| DP | Gradient同步 | 每个Optimizer Step | 中，可通过累积/重叠摊薄 |

这张表解释了为什么超节点规模首先服务模型并行通信域，而不是简单服务整个任务。

### 10.2 Ring Collective 的规模效应

对 \(r\) 个 Rank、Tensor 大小 \(M\) 的 Ring All-Reduce：

\[
T_{\text{AR}}
=
2(r-1)\alpha+
2\frac{r-1}{r}\frac{M}{BW_{\text{effective}}}
\tag{49}
\]

当 \(r\) 增大时：

- 大消息带宽项逐渐接近 \(2M/BW\)；
- 启动时延项按 \(r-1\) 増长；
- 每 Rank 计算量通常下降；
- 通信相对于计算的占比升高。

这就是 TP 不宜无限扩大的原因。更好的拓扑或层次化 Collective 可以改变常数和算法，但不能消除“每 Rank 计算减少、同步点增多”的基本趋势。

### 10.3 计算通信比

定义暴露通信占比：

\[
R_{\text{comm}}
=
\frac{T_{\text{comm,exposed}}}
{T_{\text{step}}}
\tag{50}
\]

相比简单的 \(T_{\text{comm}}/(T_{\text{compute}}+T_{\text{comm}})\)，式（50）只统计未被计算重叠隐藏的部分，更适合工程判断。

超节点规模扩大有价值的条件是：

\[
\Delta T_{\text{compute reduction}}
>
\Delta T_{\text{comm exposed}}
+
\Delta T_{\text{imbalance}}
\]

一旦不满足，已经越过该负载的扩展拐点。

### 10.4 拓扑不能只看总带宽

同样的“总带宽”可能对应完全不同的应用性能：

- 每 NPU 注入带宽是否足够；
- 任意两组之间是否无收敛；
- All-to-All 是否发生热点；
- 跨层、跨柜跳数是多少；
- 多个并行组同时运行时是否争用；
- 故障或降级路由后是否维持带宽。

因此，产品规格至少应给出：

```text
单 NPU 注入/接收能力
典型 Collective 有效带宽
不同 rank 数下的时延曲线
All-to-All 双向吞吐
多作业并发下的隔离能力
```

仅给一个 Fabric 聚合带宽，无法支撑模型并行规模判断。

### 10.5 推荐的拓扑映射原则

优先级通常为：

```text
第一优先：TP
第二优先：高频 EP、CP
第三优先：PP
第四优先：DP、推理副本
```

例外情况包括：

- MoE模型中 EP 可能比 TP 更敏感；
- 超长序列下 CP 可能成为最大流量；
- 大梯度、短 Step 的 DP 也可能需要高速域；
- PD 分离的 KV 突发可能要求专用高带宽路径。

所以正确做法不是固定优先级，而是先算每类通信的消息量和频率，再映射拓扑。

## 11. 从单场景需求归纳产品规模

### 11.1 不预设一个“万能卡数”

不同负载的高频通信域差异明显：

| 场景 | 典型高频域 | 扩大规模的主要收益 | 主要拐点 |
|---|---|---|---|
| 中等 Dense 推理 | 小 TP | 权重与KV可装入 | TP通信超过时延收益 |
| 大 Dense 训练 | TP×CP | 切分单层、长序列 | Collective 暴露 |
| 高专家 MoE训练 | TP×EP | 专家驻留、A2A本地化 | 小消息、负载倾斜 |
| 长序列训练 | TP×CP | Activation与Attention切分 | KV交换 |
| 离线推理 | 小TP×多副本 | 总吞吐 | 副本调度与HBM容量 |
| PD分离 | P组+D组 | 独立扩容 | KV传输与Incast |

因此，产品可以按“可有效容纳的高频并行域”定义档位，而不是先拍脑袋确定固定卡数。

### 11.2 三类技术档位

#### 基础型

目标：

- 中小 Dense 模型训练；
- 单模型在线推理；
- 多副本离线推理；
- 较小 TP 或 TP×CP。

关键能力：

- 单组低时延 TP；
- 足够 HBM 容纳常见推理副本；
- 支持多个小并行组隔离运行。

#### 均衡型

目标：

- 大 Dense 模型训练；
- 中等规模 MoE；
- 长上下文训练和推理；
- 中等 TP×EP/CP。

关键能力：

- 更大的无收敛集合通信域；
- EP All-to-All；
- 灵活切分成多个较小子域。

#### 大规模型

目标：

- 高专家数 MoE；
- 超长序列；
- 需要大 TP×EP×CP 的单任务；
- 大规模统一编址与资源池化。

关键能力：

- 大规模 All-to-All 与低尾延迟；
- 层次化并行与拓扑感知调度；
- 热点专家缓解；
- 大节点内部的故障隔离和子域划分。

### 11.3 产品规模的负载覆盖函数

设目标负载集合为 \(\mathcal W\)，负载 \(w\) 所需高频组规模为 \(g_w\)，超节点规模为 \(G\)。最简单的容量覆盖率：

\[
Coverage(G)
=
\frac{
\sum_{w\in\mathcal W}\omega_w
\mathbf{1}(g_w\le G)
}{
\sum_{w\in\mathcal W}\omega_w
}
\tag{51}
\]

\(\omega_w\) 表示该负载在目标市场中的权重。

但“放得下”不等于“性能好”，还应加入扩展效率：

\[
EffectiveCoverage(G)
=
\frac{
\sum_{w\in\mathcal W}\omega_w
\mathbf{1}(g_w\le G)
E_w(G_w)
}{
\sum_{w\in\mathcal W}\omega_w
}
\tag{52}
\]

其中 \(G_w\) 是在该产品上为负载 \(w\) 选择的实际子域，不一定等于整机规模。

这说明大超节点必须具备灵活子域能力。否则小任务被迫使用过大的通信域，规模越大反而越低效。

### 11.4 面向客户的选型矩阵

| 客户输入 | 首先计算 | 然后选择 | 最后验证 |
|---|---|---|---|
| Dense训练模型、Token目标 | 状态与Activation | TP/PP/DP/CP | MFU、Step时间 |
| MoE训练、E/K/Batch | 专家状态、单专家Token | TP×EP×CP | A2A、负载倾斜 |
| 在线推理、SLO与长度分布 | 权重、KV高水位 | 最小有效TP×副本 | P99 TTFT/TPOT |
| 离线推理、总Token量 | 权重与Batch | 小TP×多副本 | 总吞吐 |
| PD分离、到达率 | KV传输与P/D工作量 | P组、D组和网络 | 突发、Incast |

### 11.5 必须保留的弹性

技术上更大的超节点只有在以下能力同时存在时，才能覆盖小负载：

- 可划分独立 HCCL 通信域；
- 子域之间带宽和故障隔离；
- 调度器能够感知拓扑；
- 内存和专家可以按子域放置；
- 多作业并发不会显著干扰。

因此，产品规格除了“最大 NPU 数”，还应描述“最小可调度粒度”和“高效子域集合”。

### 12.3 算例一：70B Dense 模型训练

#### 输入

- \(P=70\) Billion；
- BF16/FP16混合精度 Adam，按 16 Bytes/Parameter；
- 每 Rank 为 Activation、通信和 Workspace 预留 30 GB；
- 暂不考虑 ZeRO。

训练状态：

\[
M_{\text{state}}
=70\times10^9\times16
=1.12\ \text{TB}
\]

单 Rank 可用于训练状态的容量：

\[
M_{\text{state budget}}
=144\times85\%-30
=92.4\ \text{GB}
\]

容量下界：

\[
N_{\text{memory}}
=
\left\lceil\frac{1120}{92.4}\right\rceil
=13
\]

13 不利于常见并行切分，可选择 16 Rank 模型并行组。例如：

```text
TP=8，PP=2
模型并行组=16
高频TP域=8
```

#### 结论

- **最小可运行规模：** 本示例假设下至少 13 Rank；
- **工程候选规模：** 向并行友好粒度取 16；
- **超节点高速域下界：** 若 PP 可跨域，核心高频域是 TP=8，而不是整个训练集群；
- **集群总规模：** 由目标 Token/s 和 DP 数进一步决定。

该算例说明，容量可能要求 16 Rank模型组，但单超节点是否必须至少 16 卡，还取决于 PP 是否跨超节点以及 Stage 边界性能。

如果采用 ZeRO-3，容量下界会明显下降，但参数 All-Gather 会增加；不能只凭容量公式断言其训练速度更快。

### 12.4 算例二：高专家数 MoE 训练

#### 输入

- 总参数量：671B；
- 每 Token 激活参数：37B；
- Routed Experts：\(E=256\)；
- Top-K：\(K=8\)；
- Hidden Size：\(H=7168\)；
- 一个 EP 组在该层处理 \(BS=16384\) Token；
- BF16 Activation：\(b_a=2\) Bytes；
- 训练状态按 16 Bytes/Parameter；
- 每 Rank 非状态内存预留 20 GB。

训练状态：

\[
M_{\text{state}}
=671\times10^9\times16
=10.736\ \text{TB}
\]

单 Rank 状态预算：

\[
144\times85\%-20=102.4\ \text{GB}
\]

容量下界：

\[
N_{\text{memory}}
=
\left\lceil\frac{10736}{102.4}\right\rceil
=105
\]

可选并行友好规模 128，例如：

```text
TP=2
EP=64
TP×EP=128
```

若 256 个专家均匀放置，每个 EP Rank 约持有 4 个专家。

单专家平均 Assignment：

\[
\bar n_x
=
\frac{16384\times8}{256}
=512
\]

一次前向的 EP 组级远端 Payload：

\[
V_{\text{EP,fwd}}^{\text{remote}}
\approx
2\times16384\times8\times7168\times2
\left(1-\frac1{64}\right)
\approx3.70\ \text{GB}
\]

单 Rank 平均发送量约为：

\[
\frac{3.70}{64}\approx57.8\ \text{MB/MoE layer forward}
\]

训练前向加反向约再乘 2，且实际还包含元数据、对齐、TP通信和路由不均。

#### 结论

- **容量候选：** 约 105 Rank，下一个典型并行粒度为 128；
- **高频域候选：** TP×EP=128；
- **超节点价值：** 若 128 Rank位于同一高带宽域，EP All-to-All无需跨越较低速Scale-out网络；
- **扩展风险：** 继续增加 EP 不会降低总逻辑 Payload，却会增加 Peer 数并降低单专家 Token 数；
- **必须实测：** All-to-All尾延迟、专家负载倾斜、小GEMM效率。

这里的 671B/37B/256/8 是参数化场景，不代表 Atlas 950 的官方推荐模型配置。

### 12.5 算例三：70B、128K长上下文在线推理

#### 输入

- 70B Dense模型；
- BF16权重；
- \(L=80\)；
- GQA：\(N_{\text{KV}}=8\)；
- \(D_{\text{head}}=128\)；
- BF16 KV：\(b_{kv}=2\) Bytes；
- 上下文长度：128 Ki Token，即 131072 Token；
- 并发：32；
- 暂按逻辑KV容量计算，不计TP复制。

每 Token KV：

\[
m_{\text{KV/token}}
=2\times80\times8\times128\times2
=327680\ \text{Bytes}
=320\ \text{KiB}
\]

单请求 128 Ki上下文：

\[
M_{\text{KV/request}}
=320\ \text{KiB}\times131072
=40\ \text{GiB}
\]

32 并发：

\[
M_{\text{KV,total}}
=32\times40
=1280\ \text{GiB}
\]

BF16权重约 140 GB。忽略其他开销时，总量约 1.51 TB（十进制）。按每卡规划可用 122.4 GB：

\[
N_{\text{memory}}
\approx
\left\lceil\frac{1514}{122.4}\right\rceil
=13
\]

向常见并行粒度取整，可得到 16 Rank候选。

#### TP复制风险

本例 \(N_{\text{KV}}=8\)。如果使用 TP=16 且框架在 \(TP>N_{\text{KV}}\) 时复制KV Head，全组物理KV可能高于逻辑值，极端简化下放大约 2 倍。

这时不能继续使用“总KV/16”的公式，候选规模可能从 16 上升到更高档，或者改用：

- TP=8并配合其他内存方案；
- CP/序列维切分；
- KV量化；
- Prefix Cache共享；
- HBM/DDR/UB分层；
- 降低并发或上下文高水位。

#### 结论

长上下文推理的规模可能由 KV 而不是权重决定。GQA 已显著降低逻辑 KV，但 TP 与 KV Head映射可能重新引入物理复制。产品选型必须读取目标框架的实际KV布局。

### 12.6 算例四：PD 分离的 KV 传输

沿用算例三，单个 128 Ki Prompt 的逻辑 KV 约为 40 GiB。

假设：

- 完成 Prefill 的请求到达 Decode池速率为 2 Request/s；
- 网络有效效率为 70%；
- 暂不考虑TP重排和协议放大。

平均KV产生速率：

\[
BW_{\text{payload}}
=2\times40
=80\ \text{GiB/s}
\]

链路能力需求：

\[
BW_{\text{required}}
\ge
\frac{80}{0.7}
\approx114.3\ \text{GiB/s}
\]

如果按4倍短时突发规划：

\[
BW_{\text{burst}}
\approx457\ \text{GiB/s}
\]

这仍不能直接与“单芯片 2 TB/s 互联带宽”作一对一结论，因为还需要知道：

- 2 TB/s 的方向和统计口径；
- P、D两侧每Rank的注入/接收上限；
- TP布局变化产生的Repartition；
- 多请求Incast；
- 逐层传输能否与Prefill重叠；
- Fabric路径和其他通信是否争用。

#### 结论

PD分离的平均带宽往往不是唯一问题，P99 Prompt、突发和目的端Incast更容易决定超节点边界。大规模超节点的价值不仅是聚合带宽，还包括在统一高速域内灵活划分P组、D组并完成KV搬运。

### 12.7 950 算例给产品定义的启示

1. **64卡扩展粒度适合成为分析基本单元。**  
   路线图披露以64卡为步长扩展，产品评估应重点测64卡子域及其倍数，而不是只测最大规模。

2. **1024卡真机应重点验证子域能力。**  
   对很多Dense推理和训练负载，高效并行组远小于1024。能否稳定划分为多个64/128卡高速域，决定多负载覆盖能力。

3. **8192卡价值主要面向大高频域和池化。**  
   高专家MoE、超长序列和统一资源池最可能受益；普通模型不应被迫使用8192卡通信域。

4. **统一编址容量不能替代性能分层。**  
   应分别公布和实测HBM、本地DDR、远端/池化内存的容量、带宽、时延和并发访问表现。

5. **路线图峰值不等于客户性能。**  
   客户选型最终需要模型级MFU、HCCL有效带宽、TTFT、TPOT和All-to-All尾延迟。

---

## 13. 结论与建议

### 13.1 影响超节点规模的五个关键因素

1. **模型总参数量**  
   决定权重和训练状态容量，MoE尤其明显。

2. **每 Token 激活参数量**  
   决定主要计算量；MoE不能用总参数量直接估算每Token FLOPs。

3. **序列长度与并发**  
   训练侧影响Attention和Activation，推理侧影响KV Cache和KV读取。

4. **高频并行域**  
   TP、EP、CP产生逐层或逐MoE层通信，决定哪些Rank值得位于同一Scale-up域。

5. **性能目标**  
   没有训练Token/s、TTFT、TPOT、吞吐或扩展效率目标，只能求容量下界，不能求唯一推荐规模。

### 13.2 对产品规格定义的建议

超节点产品不应只给“最大卡数”，还应给出：

- 可高效运行的子域尺寸；
- 不同Rank数、消息大小下的HCCL曲线；
- All-to-All单Rank注入、双向吞吐和P99时延；
- HBM及各级池化内存的独立性能；
- 拓扑感知调度和多作业隔离；
- TP×EP×CP组合的模型级扩展效率。

产品规模建议采用三档负载定义，而不是在本文阶段预设固定卡数：

| 档位 | 主要负载 | 规模决定因素 |
|---|---|---|
| 基础型 | Dense推理、中小模型训练 | 最小有效TP和副本密度 |
| 均衡型 | 大Dense、中型MoE、长上下文 | TP×EP或TP×CP |
| 大规模型 | 高专家MoE、超长序列、统一资源池 | TP×EP×CP及A2A能力 |

后续可把目标市场模型集合代入式（51）、式（52），比较64、128、256、512、1024等候选子域的有效覆盖率。

### 13.3 对客户选型的建议

#### 训练

1. 用训练状态和Activation求容量下界；
2. 用目标Token/s求算力下界；
3. 用TP/EP/CP确定高频域；
4. 用PP/DP扩展集群总规模；
5. 用HCCL和端到端MFU寻找拐点。

#### 推理

1. 用权重和KV高水位求单副本容量；
2. 选择能满足容量的最小TP；
3. 分别验证TTFT和TPOT；
4. 吞吐优先通过Batch和副本扩展；
5. PD分离时按P99 Prompt和突发计算KV网络。

### 13.4 最重要的判断

> 单超节点规模应该覆盖“高频通信模型并行组”，集群总规模应该覆盖“总吞吐和总训练速度”。把这两者混为一谈，是超节点规模规划中最常见的错误。

### 13.5 仍需通过实测回答的问题

- 昇腾目标精度和模型上的可持续算力效率；
- 不同消息大小、Rank数和拓扑下的HCCL有效带宽；
- 64/128/256/512/1024 Rank All-to-All的P99时延；
- TP、EP、CP通信计算重叠比例；
- 不同专家数、Top-K和Batch下的小GEMM效率；
- GQA/MQA在TP大于KV Head数时的实际KV布局；
- UB池化内存用于KV时的命中率、带宽和尾延迟；
- 多作业并发下的子域隔离能力。

这些数据完成后，本文的参数化模型就可以从“规模候选生成器”升级为“产品规格决策模型”。
