# 稀疏大模型负载驱动的昇腾超节点规模需求分析

> **精华版｜约8页**
> **用途：** 超节点产品规格讨论、客户负载选型与技术评审
> **日期：** 2026-08-11

---

## 1. 核心结论与规模判断

稀疏MoE模型已经成为大模型扩展的重要方向。其基础特点是：全部专家权重需要占用内存，但每个Token只激活其中少量专家。因此，超节点规模同时受到**总参数容量、激活参数算力、专家通信和长序列KV**四类约束。

超节点规模分析需要区分三个层次：

| 层次 | 含义 |
|---|---|
| 最小可运行规模 | 权重、训练状态、Activation或KV能够装入 |
| 性能推荐规模 | TP、EP、CP高频通信能够在高速互联域内高效执行 |
| 集群总规模 | 通过PP、DP或推理副本满足总训练速度和服务吞吐 |

产品定义侧的核心原则为：

> 单超节点优先容纳高频模型并行组，集群总规模负责承载数据并行、流水线并行和推理副本。

不同负载的主要规模驱动因素如下。

| 负载 | 容量驱动因素 | 性能驱动因素 | 超节点内优先并行域 |
|---|---|---|---|
| MoE训练 | 全部专家训练状态、Activation | EP All-to-All、TP集合通信、专家倾斜 | TP×EP，长序列时加入CP |
| MoE在线推理 | 全部专家权重、KV Cache | 小Batch专家计算、EP通信、TPOT | TP×EP |
| 长上下文推理 | KV Cache高水位 | KV读取、Prefill计算、调度 | TP×CP或KV分层 |
| PD分离推理 | Decode侧KV容量 | Prefill算力、Decode带宽、KV传输 | 独立P组、D组及高速KV通道 |

超节点扩大并非始终带来线性收益。并行规模增加后，每张NPU承担的计算减少，通信启动时延、All-to-All Peer数量和负载不均占比上升。推荐规模位于容量充足、计算饱满和通信可控的交叉区域。

## 2. 稀疏模型的关键负载参数

MoE规模分析只需要抓住以下变量。

| 参数 | 影响 |
|---|---|
| 总参数量 \(P_{\text{total}}\) | 权重和训练状态容量 |
| 激活参数量 \(P_{\text{active}}\) | 每Token主要计算量 |
| 专家总数 \(E\) | 专家权重容量、EP规模和Peer数量 |
| Top-K \(K\) | 单Token专家计算和路由Payload |
| 隐藏维度 \(H\) | 专家计算和通信消息大小 |
| 序列长度 \(S\) | 训练Attention、Activation及推理KV |
| Batch与并发 \(C\) | 单专家Token数量、KV高水位和吞吐 |

设每个Routed Expert参数量为 \(P_x\)，MoE层数为 \(L_{\text{MoE}}\)，非专家参数为 \(P_{\text{nonexpert}}\)：

\[
\begin{aligned}
P_{\text{total}}&\approx P_{\text{nonexpert}}+L_{\text{MoE}}E P_x,\\
P_{\text{active}}&\approx P_{\text{nonexpert}}+L_{\text{MoE}}K P_x
\end{aligned}
\tag{1}
\]

总参数量主要决定容量，激活参数量主要决定计算。增加专家总数 \(E\) 而保持Top-K不变，会显著增加权重容量，但不会同比增加单Token理论FLOPs。

专家数增加仍会间接降低效率：

- EP规模和All-to-All Peer数量增加；
- 单专家平均Token数量下降；
- 专家GEMM变小；
- 热门专家和Rank尾部延迟增大；
- 专家复制与Shared Expert增加额外容量。

一个EP通信组包含 \(B S\) 个Token时，单专家平均Assignment数量为：

\[
\bar n_x=\frac{BSK}{E}
\tag{2}
\]

\(\bar n_x\) 过小会使专家矩阵乘无法充分利用NPU。该阈值需要根据专家宽度、精度和目标NPU实测确定。

## 3. 容量、算力与通信推导框架

### 3.1 容量下界

设模型、训练状态、Activation或KV的总驻留量为 \(M_{\text{total}}\)，单NPU HBM为 \(M_{\text{HBM}}\)，规划利用率为 \(\eta_M\)：

\[
N_{\text{memory}}
=
\left\lceil
\frac{M_{\text{total}}}
{M_{\text{HBM}}\eta_M}
\right\rceil
\tag{3}
\]

\(\eta_M\)用于保留系统不可分配空间、框架保守水位和未建模峰值；\(M_{\text{total}}\)仍需显式计入Activation、通信Buffer和Runtime Workspace。聚合容量下界只用于排除过小方案，实际布局还需满足TP、EP、CP和PP的整除及复制约束。

### 3.2 算力下界

目标时间 \(T_{\text{target}}\) 内需要完成 \(F_{\text{required}}\) FLOPs，单NPU峰值算力为 \(F_{\text{peak}}\)，模型有效效率为 \(\eta_F\)：

\[
N_{\text{compute}}
=
\left\lceil
\frac{F_{\text{required}}}
{F_{\text{peak}}\eta_FT_{\text{target}}}
\right\rceil
\tag{4}
\]

\(\eta_F\)必须使用目标模型、精度和Batch的实测值。芯片峰值不能直接替代可持续模型性能。

### 3.3 EP通信

一个EP组处理 \(BS\) 个Token，每个Token向 \(K\) 个专家发送 \(H\) 维Activation，每元素 \(b_a\) 字节。完整前向包含Dispatch和Combine：

\[
V_{\text{EP,fwd}}^{\text{remote}}
\approx
2BSKHb_a
\left(1-\frac1{EP}\right)
\tag{5}
\]

式（5）表示EP组级前向远端Payload。训练反向还需传输相应梯度，理想情况下前向加反向的总Payload约为式（5）的2倍。单Rank平均发送量还需除以EP，但热门专家所在Rank的峰值接收量可能显著高于平均值；Fabric实际流量还受到路由跳数、协议和拥塞影响。

### 3.4 通信时间与扩展效率

\[
T_{\text{comm}}
\approx
n_\alpha\alpha+
\frac{V_{\text{comm}}}{BW_{\text{effective}}}
\tag{6}
\]

小消息主要受启动时延 \(\alpha\) 影响，大消息主要受有效带宽影响。All-to-All Peer数量扩大后，单Peer消息变小，时延和调度开销可能先于总字节量成为瓶颈。

标准正交并行布局下，高频通信域近似为：

\[
N_{\text{high-freq}}
\approx TP\times EP\times CP
\tag{7}
\]

PP、DP和推理副本通常更适合跨超节点扩展。式（7）是候选边界，最终规模仍需通过HCCL和模型级Benchmark验证。

## 4. MoE训练的超节点需求

经典BF16/FP16混合精度Adam训练可用16 Bytes/Parameter估算权重、梯度、FP32 Master Weight和两份Optimizer State：

\[
M_{\text{state}}\approx16P_{\text{total}}
\tag{8}
\]

真实单Rank内存必须拆分为：

```text
可由EP切分的Routed Expert状态
+ 仅由TP/PP切分的非专家状态
+ Shared/复制状态
+ Activation、通信与Workspace
```

只用“总参数量÷总卡数”会高估EP的切分能力。EP只切专家参数，Attention、Router、Embedding和Shared Expert需要按实际布局计算。

MoE训练的高频通信主要包括：

1. **TP通信**：每层发生All-Reduce、All-Gather或Reduce-Scatter；
2. **EP通信**：每个MoE层执行Token Dispatch和Combine；
3. **CP通信**：长序列Attention交换KV；
4. **PP通信**：Stage边界传输Activation；
5. **DP通信**：Optimizer Step同步梯度。

拓扑映射优先级通常为：

```text
超节点内：TP×EP，长序列时扩展为TP×EP×CP
超节点间：PP×DP
```

MoE训练的推荐规模需要同时满足：

- 全部训练状态和Activation可装入；
- 非专家状态不会因EP复制而超出HBM；
- 单专家Assignment数量保持计算饱满；
- EP All-to-All不跨越低速网络；
- 通信暴露时间低于专家计算时间；
- 专家负载倾斜处于可接受范围。

专家数增加不会直接放大式（5）的基本Payload，但会增加Peer数量、减少每Rank专家计算并加重小消息比例。专家数与超节点规模之间并非简单的一一对应关系。

长序列训练还会引入 \(O(S^2H)\) Attention计算。FlashAttention降低中间存储和HBM访问，但不改变精确Attention的平方计算主项。CP可以切分序列与单Rank计算，同时增加逐层KV交换。

## 5. MoE推理的超节点需求

MoE推理同时受到全部专家权重、激活专家计算、KV Cache和EP通信约束。

### 5.1 权重与专家驻留

全部专家通常需要驻留在HBM或可接受的分层内存中。推理权重容量近似为 \(M_W\approx P_{\text{total}}b_w\)。

量化后仍需加入Scale、Zero Point、Padding、未量化层和反量化Workspace。MoE每轮实际读取的专家权重由Batch内访问专家的并集决定，不能直接使用单Token激活参数估算HBM流量。

### 5.2 KV Cache

层数为 \(L\)、KV Head数为 \(N_{\text{KV}}\)、Head维度为 \(D_{\text{head}}\)，KV每元素 \(b_{kv}\) 字节：

\[
\begin{aligned}
m_{\text{KV/token}}&=2L N_{\text{KV}}D_{\text{head}}b_{kv},\\
M_{\text{KV,total}}&=m_{\text{KV/token}}\sum_{i=1}^{C}\ell_i
\end{aligned}
\tag{9}
\]

容量规划应使用P95/P99驻留高水位。TP大于KV Head数时，部分框架会复制KV Head；此时每Rank KV不能简单除以TP。

### 5.3 Prefill、Decode与副本

- Prefill处理大量Prompt Token，主要受矩阵计算和长序列Attention约束；
- Decode每轮生成少量Token，主要受权重/KV读取、EP通信和TPOT约束；
- 在线服务优先选择最小可行模型并行布局，吞吐通过副本扩展；
- 离线服务可以提高Batch，优先保持专家GEMM饱满。

小Batch MoE Decode容易同时出现小专家GEMM和大量All-to-All小消息。扩大EP可以降低每Rank权重，却可能增加通信Peer和尾部延迟。

### 5.4 PD分离

PD分离将Prefill和Decode部署到不同资源池。请求到达率为 \(\lambda\)，网络有效效率为 \(\eta_{\text{network}}\)：

\[
\begin{aligned}
D_{\text{KV}}&=2LSN_{\text{KV}}D_{\text{head}}b_{kv},\\
BW_{\text{PD}}&\ge
\frac{\lambda\mathbb E[D_{\text{wire}}]}{\eta_{\text{network}}}
\end{aligned}
\tag{10}
\]

PD分离支持P组和D组独立扩容，但增加KV传输、TP布局重排和目的端Incast。平均带宽之外还需校验P99 Prompt长度和短时突发。

## 6. 通信域与超节点边界

| 并行方式 | 主要通信 | 频率 | Scale-up优先级 |
|---|---|---:|---|
| TP | All-Reduce/All-Gather/Reduce-Scatter | 每层 | 很高 |
| EP | All-to-All Dispatch/Combine | 每个MoE层 | 很高 |
| CP | KV Ring/All-Gather | 每个Attention层 | 高 |
| PP | Stage边界点对点 | 每个Micro Batch | 中 |
| DP | 梯度同步 | 每个Optimizer Step | 中 |

超节点边界由通信频率、消息大小、有效带宽和计算重叠共同确定。单纯使用Fabric聚合带宽无法支撑规模判断，产品规格还需要给出：

- 单NPU注入与接收带宽；
- 不同Rank数、消息大小下的HCCL算法带宽；
- All-to-All双向吞吐和P99时延；
- 64/128/256/512/1024卡子域效率；
- 多作业并发和故障降级下的带宽保持能力。

大超节点还需要灵活子域能力。较小MoE任务不应被迫使用整个通信域，子域之间需要具备带宽隔离、故障隔离和拓扑感知调度。

规模扩展停止条件包括：

- 扩展效率低于产品目标；
- 通信暴露时间开始主导Step时间；
- 单专家Token数量低于高效GEMM阈值；
- 专家倾斜使最慢Rank主导尾延迟；
- 推理TPOT不再改善；
- 增加EP后Per-peer消息过小。

## 7. Atlas 950参数化算例

### 7.1 公开口径

| 状态 | 公开参数 | 使用边界 |
|---|---|---|
| 1024卡真机，2026-07-17公开 | 1 EFLOPS FP8、2 EFLOPS FP4、256 TB统一编址空间、约3 μs RTT | 统一编址空间不等于HBM；未公开精确总互联带宽 |
| 8192卡路线图 | 8 EFLOPS FP8、16 EFLOPS FP4、1152 TB总内存、约16 PB/s互联 | 路线图计划参数，不作为已交付实测 |
| Ascend 950DT路线图 | 144 GB HBM、4 TB/s HBM带宽、2 TB/s芯片互联 | 用于示例，应用有效值仍需Benchmark |

### 7.2 MoE训练示例

示例输入：

- 总参数671B，激活参数37B；
- 256个Routed Experts，Top-8；
- 97.5%参数为Routed Expert，2.5%为非专家参数，该比例代入式（1）得到约37.2B激活参数；
- Routed Expert按 \(TP_x\times EP\times PP\) 切分，非专家参数按 \(TP\times PP\) 切分；
- \(TP_x=TP=2,EP=64,PP=8\)；
- 85%规划容量内再为Activation、通信和Workspace预留20 GB；
- HBM规划利用率85%。

训练状态总量约为 \(671\times10^9\times16=10.736\ \text{TB}\)。

在上述参数拆分假设下，每RankRouted Expert状态约10.2 GB，非专家状态约16.8 GB，训练状态合计约27.0 GB；加20 GB负载预留后约47.0 GB，低于122.4 GB规划容量。HBM剩余15%作为系统安全余量，与20 GB负载预留分属两层。完整模型并行组为1024 Rank，每个PP Stage内的高频TP×EP域为128 Rank。

该结果只证明容量候选。性能推荐规模仍需验证128 Rank All-to-All、专家倾斜、小GEMM效率和TP通信。

### 7.3 长上下文MoE推理示例

示例模型：

- 总参数400B、激活参数40B；
- FP8权重约400 GB；
- 64层、8个KV Head、Head维度128；
- BF16 KV；
- 128 Ki上下文、16并发。

每Token KV为256 KiB，单请求KV为32 GiB，16并发逻辑KV约512 GiB，即约550 GB。权重与KV合计约950 GB，按单NPU规划可用122.4 GB计算，逻辑聚合容量下界为8 Rank。

实际布局还需加入专家放置、TP/EP/CP、KV Head复制和Workspace。高频域通常大于聚合容量下界。

按每秒2个完整Prompt进入Decode池、网络有效效率70%计算，平均名义PD KV带宽下界约为 \(2\times32/0.7\approx91.4\ \text{GiB/s}\)。该值使用逻辑KV而非完整 \(D_{\text{wire}}\)，不含TP重排、协议开销和短时突发，不能直接与2 TB/s芯片互联峰值作性能结论。

## 8. 产品规格与客户选型建议

### 8.1 产品规格

超节点产品定义应从目标MoE负载集合出发，比较64、128、256、512和1024卡子域的有效覆盖率。

| 产品能力 | 核心指标 |
|---|---|
| 容量 | HBM、统一编址和池化内存分层能力 |
| 计算 | 目标精度下的模型级有效算力 |
| TP通信 | All-Reduce/All-Gather的算法带宽与时延 |
| EP通信 | All-to-All吞吐、Peer扩展和P99尾延迟 |
| CP通信 | 长序列KV交换和通信计算重叠 |
| 子域 | 最小调度粒度、带宽隔离和故障隔离 |

大规模产品的主要目标场景包括高专家数、长上下文和大TP×EP×CP负载。公开路线图参数尚不能证明最大规模模型级效率，仍需完成1024卡以上的扩展效率、拥塞和尾延迟验证。

### 8.2 客户选型

训练选型流程：

```text
逐层参数与专家分解
→ 训练状态和Activation容量
→ TP×EP×CP高频域
→ PP×DP集群扩展
→ HCCL与端到端MFU验证
```

推理选型流程：

```text
全部专家权重与KV高水位
→ 最小可行TP×EP×CP布局
→ TTFT与TPOT验证
→ Batch和副本扩展吞吐
→ PD传输与P99突发验证
```

### 8.3 最终判断

MoE超节点规模的技术最优点由以下条件共同决定：

1. 全部专家权重或训练状态可装入；
2. 非专家和复制状态不会因EP扩大而超出HBM；
3. 单专家Token数量保持计算饱满；
4. TP、EP和CP高频通信位于高速域；
5. 通信暴露、专家倾斜和尾部时延保持在目标范围；
6. 较小任务能够使用独立高效子域。

参数化公式用于生成候选规模，目标平台Benchmark负责确定性能推荐规模和扩展拐点。超节点最大卡数、子域效率和集群总规模需要分别定义。
